DBOS Client

A Client connects to a DBOS application's system database from outside the application: an API server that enqueues work, an operator's tool, or a service in another process or language. It runs no workflows, recovers nothing and dequeues nothing. It is cheap to clone.

let client = dbos::Client::connect(dbos::ClientConfig::from_env()).await?;
let handle: dbos::WorkflowHandle<String> =
    client.enqueue("process_order", "orders", "order-123").await?;
let result = handle.result().await?;
client.close().await;

A client has no registered workflows, so the type parameters of the handles it returns state what each workflow returns; nothing checks them until the result is decoded. Called from inside a workflow, a client's calls are not recorded: use the free functions there.

connect​

pub async fn connect(config: ClientConfig) -> dbos::Result<Client>;

Connect to the system database described by a ClientConfig.

close​

pub async fn close(&self);

Close the client's connection pool.

app_name​

pub fn app_name(&self) -> Option<&str>;

The application the client acts for, from ClientConfig::app_name.

enqueue​

pub async fn enqueue<P: Serialize, R, E>(&self, workflow: impl Into<QualifiedWorkflowName>, queue: &str, input: P) -> dbos::Result<WorkflowHandle<R, E>>;
pub async fn enqueue_with<P: Serialize, R, E>(&self, workflow: impl Into<QualifiedWorkflowName>, input: P, options: EnqueueOptions<'_>) -> dbos::Result<WorkflowHandle<R, E>>;
pub async fn enqueue_portable<R, E>(&self, workflow: impl Into<QualifiedWorkflowName>, args: PortableWorkflowArgs, options: EnqueueOptions<'_>) -> dbos::Result<WorkflowHandle<R, E>>;

Enqueue a workflow by name, with EnqueueOptions. Whichever executor has the workflow dequeues it. To enqueue a workflow written in another language, set serialization: SerializationFormat::Portable; see portable workflows.

let options = EnqueueOptions {
    workflow_id: Some("order-123"),
    ..EnqueueOptions::new("orders")
};
let handle: WorkflowHandle<String> = client.enqueue_with("process_order", "order-123", options).await?;

retrieve_workflow and workflow_status​

pub fn retrieve_workflow<R, E>(&self, workflow_id: &str) -> WorkflowHandle<R, E>;
pub async fn workflow_status(&self, workflow_id: &str) -> dbos::Result<Option<WorkflowStatus>>;

A handle to a workflow by ID, and a workflow's current status (None if there's no such workflow).

As on DBOS. Build a spec with ScheduleSpec::for_workflow, which names the workflow. A client with no app_name and a spec with none writes an unclaimed schedule, which every application sharing the database fires.

Application versions​

pub async fn list_app_versions(&self) -> dbos::Result<Vec<VersionInfo>>;
pub async fn latest_app_version(&self) -> dbos::Result<Option<VersionInfo>>;
pub async fn set_latest_app_version(&self, version_name: &str) -> dbos::Result<()>;
pub async fn set_latest_app_version_for(&self, version_name: &str, app_name: &str) -> dbos::Result<()>;

The application versions that have registered, newest first, and the latest one, which an enqueue naming no version runs on. set_latest_app_version promotes a version to latest; promoting an older one is a rollback. A client named for an application sees and promotes that application's versions; set_latest_app_version_for names the application explicitly. DBOS has the same methods, for its own application. A VersionInfo has app_name, version_id, version_name, version_timestamp and created_at.
